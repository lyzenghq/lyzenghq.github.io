# 《性能之巅》第2版 术语表

> *Systems Performance: Enterprise and the Cloud, 2nd Edition*
> Brendan Gregg, Addison-Wesley, 2020
> 位置按书中首次详细解释标注；“待补”表示截至 §1.7 尚未在已读范围内展开，后续读到时再补。

---

## 一、基础概念

| 英文 | 中文 | 释义 | 书中位置（首次详细解释） |
|------|------|------|----------------------|
| **Systems Performance** | 系统性能 | 研究计算机系统在真实负载下的效率与瓶颈，涵盖从应用到底层硬件的完整软件栈。 | §1.1 |
| **Observability** | 可观测性 | 不改代码、不施加额外负载，就能从外部输出推断系统内部状态的属性。核心是"不扰动"——与 experimental tools（实验性工具）相对，后者要主动施压去试探。 | §1.7 |
| **Full Stack** | 全栈 | 在性能语境下，指从应用一直到底层硬件（metal）的完整软件栈，包括系统库、内核和硬件本身。（注：业界这个词常指前后端开发，性能语境下指「应用→库→内核→硬件」） | §1.1 |
| **Data Path** | 数据路径 | 一个具体请求从入口到出口经过的所有组件链路。必须针对具体负载/请求来画，否则只是架构图。路径上任何环节都可能影响性能。 | §1.1 |
| **Latency** | 延迟 | 完成一项操作所需的时间，是性能优化的核心目标之一。 | §1.6 |
| **Throughput** | 吞吐量 | 单位时间内系统处理的工作量。 | 待补 |
| **Utilization** | 使用率 | 资源被占用的时间比例，如 CPU 使用率、磁盘使用率。（≠ saturation：使用率高不代表饱和，饱和的关键特征是请求在排队） | 待补 |
| **Saturation** | 饱和度 | 资源已满且有请求排队等待的状态，关键在有没有排队（≠ utilization）。如 CPU 就绪队列过长、内存不足导致换页。 | 待补 |
| **Errors** | 错误 | 资源或组件产生的错误计数，如网络丢包、磁盘 I/O 错误。 | 待补 |
| **Contention** | 争用 | 多个执行单元抢同一个资源导致的等待，如锁争用、缓存行争用、内存带宽争用。是 USE 方法之外的第四种常见瓶颈形态。 | 待补 |
| **Jitter** | 抖动 | 延迟的波动/不稳定性，即相同操作的响应时间忽高忽低。对实时系统尤其致命。 | 待补 |
| **Tail Latency / p99** | 尾部延迟 / 百分位延迟 | 长尾分布下的高百分位延迟（如 p99 = 99% 的请求延迟低于此值），比平均值更能反映真实用户体验。 | 待补 |

## 二、方法论

| 英文 | 中文 | 释义 | 书中位置（首次详细解释） |
|------|------|------|----------------------|
| **USE Method** | USE 方法 | 遍历每个系统资源，检查**使用率（U）tilization**、**饱和度（S）aturation**、**错误（E）rrors**，快速定位瓶颈。 | 待补 |
| **Workload Characterization** | 工作负载特征归纳 | 通过归纳负载的特征，区分负载问题与架构问题，避免不必要的工作。 | 待补 |
| **Downward Digging** | 向下挖掘分析 | 从高层级监测开始，逐步缩小研究范围，可使用"5个Why"技巧定位根因。 | 待补 |
| **Latency Analysis** | 延时分析法 | 将操作时间划分为多个时间段，找到耗时最大的段进行分析，定位根本原因。 | 待补 |
| **Scientific Method** | 科学法 | 假设 → 仪器检验 → 数据 → 假设，通过收集数据验证假设的诊断循环。 | 待补 |
| **Known Knowns / Known Unknowns / Unknown Unknowns** | 已知的已知 / 已知的未知 / 未知的未知 | 性能领域的认知分层：你知道的、你知道你不知道的、你不知道你不知道的。 | 待补 |
| **Amdahl's Law** | Amdahl 定律 | 系统整体加速比受限于串行部分的比例，用于评估并行优化的收益上限。 | 待补 |
| **Universal Scalability Law** | 通用扩展定律 | 在 Amdahl 定律基础上增加了串扰（contention）和交换（coherency）成本，更贴合分布式系统。 | 待补 |

## 三、观测手段

| 英文 | 中文 | 释义 | 书中位置（首次详细解释） |
|------|------|------|----------------------|
| **Experimental Tools** | 实验性工具 | 主动对系统施加负载或故障以观察反应的工具（如 stress-ng、fio、tc netem）。与 observability 的核心区别在于会对系统产生扰动，线上禁用。 | 待补 |
| **Profiling** | 剖析 | 一段时间内反复采样调用栈并按函数聚合，回答"资源花在哪个函数上"。是空间归因，不是延迟分布。（注意：火焰图宽度 ≠ 慢；不含 p99） | §1.7.2 |
| **Flame Graph** | 火焰图 | profiling 数据的可视化，宽度 = 采样次数占比（不代表单次调用慢），层级 = 调用深度。由 Brendan Gregg 发明。 | §1.7.2 |
| **Tracing** | 跟踪（追踪） | 按事件记录发生了什么及其时序，供后续分析或实时汇总。能看到哪些细节取决于可用的事件源和插桩点。 | §1.7.3 |
| **Counter** | 计数器 | 软件或内核维护的计数值，常记录累计操作数、字节数或错误数。定期读取两次计数器并计算差值，可以得到这段时间内的变化量或速率。 | §1.7.1 |
| **Statistics** | 统计量 | 从计数器或测量值计算、汇总出的量，如速率、平均值、直方图和百分位数。适合低开销地持续观察趋势，但聚合会丢失单个事件细节；平均值可能掩盖长尾，p99 更能显示尾部。 | §1.7.1 |
| **Metric** | 指标 | 为评估或监控目标而选用的统计量，通常按固定间隔记录并绘图，也可用于告警。例如请求速率、p95 延迟或 CPU 使用率。本书提醒，业界对 counter、statistics、metric 的用法并不总是严格区分。 | §1.7.1 |
| **Instrumentation / instrumenting** | 检测（也常称插桩） | Instrumentation 是名词；书中此处用 instrument 的 -ing 形式，表示通过检测点采集数据。这里是利用 execve 系统调用上的静态 tracepoint 捕获新进程事件。 | §1.7.3 |
| **Static Instrumentation** | 静态检测（静态插桩） | 检测点预先写入代码或作为固定 tracepoint 提供，观测位置固定；具体开销和启用方式取决于实现。 | §1.7.3 |
| **Tracepoint** | 跟踪点（静态检测点） | 内核预先设置的静态检测点，可用于记录磁盘 I/O、调度器、系统调用等事件；跟踪工具在这些点上采集事件数据。 | §4（§1.7.3 引入） |
| **User Statically Defined Tracing (USDT)** | 用户静态定义跟踪（USDT） | 用户态静态检测技术；应用或库可以预先定义探针，再由跟踪工具观测库调用、服务请求等事件。 | §4（§1.7.3 引入） |
| **USDT Probe** | USDT 探针 | USDT 技术中预先定义的单个用户态探针位置，用于产生可供跟踪工具采集的事件。 | §4（§1.7.3 引入） |
| **Dynamic Instrumentation** | 动态检测（动态插桩） | 软件运行时创建或附着检测点（如 kprobe / uprobe）；通常无需修改应用源代码或重启目标程序。 | §1.7.3 |
| **BPF (Berkeley Packet Filter)** | BPF（伯克利数据包过滤器） | 最初是用于加速 tcpdump 过滤表达式的小型内核虚拟机；后来扩展为具备安全机制、可快速访问资源的通用内核执行环境，并为 Linux tracing 工具提供可编程能力。本书现称这项技术为 BPF。 | §1.7.3（详解 §3） |
| **eBPF** | 扩展 BPF（旧称） | 曾用于指代扩展后的 BPF；本书说明该技术现在统一称为 BPF。 | §1.7.3 |
| **DTrace** | 动态追踪框架 | Solaris/FreeBSD/macOS 上的动态追踪技术，Gregg 早期重要研究方向。 | §1.7.3 |
| **BPF Compiler Collection (BCC)** | BPF 编译器集合（BCC） | BPF tracing 前端与工具集之一，提供编写和运行 BPF 跟踪工具的可编程能力；书中以 execsnoop 为 BCC 工具的例子。 | §15（§1.7.3 引入） |
| **bpftrace** | bpftrace | Linux 上的 BPF tracing 前端之一，可编写和运行可编程跟踪工具。 | §15（§1.7.3 引入） |
| **perf** | Linux 性能分析器 | Linux 跟踪与性能分析工具，具备与 BPF 前端相似的部分能力；本书后续专章介绍。 | §13（§1.7.3 提及） |
| **Ftrace** | 内核跟踪框架 | Linux 内核跟踪工具，具备与 BPF 前端相似的部分能力；本书后续专章介绍。 | §14（§1.7.3 提及） |
| **Linux 60-Second Checklist** | Linux 60秒检查清单 | 一分钟内快速扫过关键命令/指标的排障清单（如 uptime、vmstat、iostat、top 等），全部基于 statistics。 | 待补 |

## 四、统计与建模

| 英文 | 中文 | 释义 | 书中位置（首次详细解释） |
|------|------|------|----------------------|
| **Queueing Theory** | 排队理论 | 用数学模型描述请求在系统中的等待与处理过程，Kendall 标记法用于分类排队系统。 | 待补 |
| **Capacity Planning** | 容量规划 | 根据负载增长规划并扩展系统，包括研究资源极限和因素分析。 | §1.3 |
| **Microbenchmarking** | 微基准测试 | 施加简单的人造工作负载进行测试，如系统调用、文件系统读取、网络吞吐量。 | 待补 |
| **Baseline Statistics** | 基础线统计 | 将当前性能指标与历史数值做比较，判断是否偏离正常范围。 | 待补 |
| **Benchmark** | 基准测试 | 在可控环境下进行的标准化性能测量，强调可比性和可重复性。（与 load test 的区别：benchmark 追求可控可比，load test 追求模拟真实流量） | 待补 |
| **Load Test** | 负载测试 | 模拟真实流量对系统进行测试，强调真实性而非可控性。 | 待补 |
| **Regression** | 性能回退 | 系统更新后性能指标相比基线下降的现象，需在 CI/CD 中自动化检测。 | 待补 |
| **Reproducibility** | 可复现性 | 性能问题能在测试环境中稳定复现的能力。Gregg 强调"不能复现的问题不值得花太多时间查"。 | 待补 |

## 五、系统与组件

| 英文 | 中文 | 释义 | 书中位置（首次详细解释） |
|------|------|------|----------------------|
| **CPI / IPC** | 每指令周期数 / 每周期指令数 | CPU 效率指标，CPI 越低 / IPC 越高表示 CPU 执行效率越好。 | 待补 |
| **Cache** | 缓存 | 高速存储层，用于减少对慢速存储的访问，缓存颠簸（thrashing）是过载时性能骤降的重要因素。 | 待补 |
| **Virtual Memory** | 虚拟内存 | 操作系统提供的内存抽象，涉及换页（paging）和交换（swapping）。 | 待补 |
| **Context Switch** | 上下文切换 | CPU 从一个进程/线程切换到另一个时的状态保存与恢复操作。 | 待补 |
| **SLA / SLO** | 服务等级协议 / 服务等级目标 | SLA 是服务商与客户之间的书面协议，SLO 是具体的性能目标值。 | 待补 |

## 六、反方法（Anti-Methods）

| 英文 | 中文 | 释义 | 书中位置（首次详细解释） |
|------|------|------|----------------------|
| **Streetlight Anti-Method** | 街灯反方法 | 只在"灯下"（容易观测的地方）找问题，而不是在问题真正存在的地方。 | 待补 |
| **Random Change Anti-Method** | 随机变动反方法 | 没有假设和测量，随意修改配置，指望碰巧解决问题。 | 待补 |
| **Blame Others Anti-Method** | 责怪他人反方法 | 将问题归咎于其他团队或组件，而不进行系统性排查。 | 待补 |
